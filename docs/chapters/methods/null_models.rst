===================
Spatial null models
===================

The null-model layer is shared by the correlation and PLS workflows. Its role
is to create permuted imaging maps that preserve more spatial structure than a
naive random shuffle.

Why a spatial null is needed
----------------------------

Brain maps are spatially autocorrelated: nearby regions often have similar
values. If this structure is ignored, gene-map associations can look more
significant than they really are because the effective number of independent
observations is smaller than the raw number of regions.

The toolbox therefore permutes the imaging map rather than the gene-expression
matrix and, whenever possible, uses cortical null models that preserve spatial
structure on the cortical surface.

How nulls enter the workflows
-----------------------------

For a selected atlas subset with ``n`` regions and ``B`` permutations, the
null-model layer returns an ``n x B`` matrix of permuted imaging values.

That same permuted matrix is then reused downstream:

- ``corr`` correlates every gene against every permuted imaging vector
- ``pls`` refits the PLS model against every permuted imaging vector

This design keeps the null definition consistent across gene-level and
component-level inference.

Hybrid cortical and non-cortical handling
-----------------------------------------

Many atlases contain both cortical and non-cortical rows. The toolbox handles
them separately:

- cortical rows use the requested cortical null model when available
- non-cortical rows are shuffled within hemisphere-aware groups

In practice this means a mixed atlas such as ``dk`` can produce a hybrid null
matrix:

- cortical entries generated by a surface-based spatial null
- subcortical entries generated by grouped random shuffling

This is expected behavior, not a fallback bug.

Available null methods
----------------------

``auto``
~~~~~~~~

``auto`` is the default because it tries to use the best available cortical
null without forcing the user to know surface-asset details in advance.

The current order is:

1. try ``vasa``
2. if that fails, try ``alexander_bloch``
3. if surface nulls remain unavailable, fall back to grouped random shuffling

``vasa``
~~~~~~~~

``vasa`` is a surface-based cortical null exposed through ``neuromaps``. It
requires:

- the ``maps`` extra
- a compatible cortical surface representation for the selected atlas
- the needed surface geometry assets in the ``neuromaps`` cache

``alexander_bloch``
~~~~~~~~~~~~~~~~~~~

This is another ``neuromaps`` surface-null option for cortical data. It has
similar practical requirements to ``vasa`` and is often used as a fallback
when ``vasa`` is unavailable.

``moran``
~~~~~~~~~

``moran`` is exposed through the same framework and is available for
surface-based cortical null generation. It also depends on the relevant
surface assets.

``random``
~~~~~~~~~~

``random`` is a grouped random shuffle. It does not attempt to preserve
cortical spatial structure, but it is useful:

- as an explicit baseline
- when surface dependencies are unavailable
- for debugging and lightweight smoke tests

Grouped random shuffling
------------------------

When random shuffling is used for non-cortical rows, the toolbox does not
shuffle all rows together blindly. Instead it shuffles within grouped labels
that preserve the high-level hemisphere structure. This prevents obviously
invalid left-right swaps in situations where the atlas subset is expected to
respect hemisphere boundaries.

Practical guidance
------------------

- use ``auto`` unless you need a specific null family for reproducibility
- use ``random`` when you want to avoid surface-null dependencies entirely
- expect mixed cortical/subcortical null generation in atlases that contain
  both region types
- expect a warning when ``auto`` cannot obtain a surface-based null and falls
  back to grouped random shuffling

Runtime considerations
----------------------

Null generation is often much cheaper than the downstream gene statistics,
especially for PLS or for enrichment runs. Still, two things matter:

- larger ``B`` improves p-value resolution but increases runtime
- surface-based nulls depend on ``neuromaps`` assets being installed and
  discoverable

If a run unexpectedly falls back to random shuffling, first check:

- whether the ``maps`` extra is installed
- whether ``NEUROMAPS_DATA`` points to a writable cache
- whether the selected atlas has compatible surface assets for the requested
  method
